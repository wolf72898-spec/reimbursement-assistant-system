# 提示词2 · 技术架构方案（完整版）

> 角色：资深 Python 后端架构师 | 项目：报销助手智能体系统
> 约束：FastAPI（异步）+ Python 3.11+；LLM 走 API 可换供应商；制度文档向量化检索；两角色（员工问答+报销 / 管理员维护知识库+看记录）

---

## 一、四层架构图（文字版）

```
┌─ 入口层 ──────────────────────────────────────────────┐
│  Web 前端（Vue3/React 均可）                            │
│  ├─ 员工端：对话窗口 + 我的报销单                        │
│  ├─ 管理端：制度知识库管理 + 报销记录看板                 │
│  └─ 通信：REST（业务操作）+ SSE（对话流式输出，二期）      │
│  鉴权：JWT（登录后颁发，角色写在 claims）                 │
├─ 服务层（FastAPI 异步）──────────────────────────────┤
│  ├─ 认证与权限服务：登录、RBAC（employee/admin 两角色）   │
│  ├─ 会话服务：对话会话与消息的增查                        │
│  ├─ 报销单服务：草稿 CRUD、状态流转（draft → submitted）  │
│  ├─ 知识库服务：制度文档上传/解析/切分/向量化/版本管理      │
│  └─ 审计日志：关键操作留痕（谁上传了制度、谁改了草稿）      │
├─ 智能体编排层 ────────────────────────────────────────┤
│  ├─ 意图路由：判断用户想"问答"还是"发起报销"              │
│  ├─ RAG 检索工具：问题 → 混合检索制度切片 → 组装上下文     │
│  ├─ 表单抽取工具：对话文本 → 报销单字段（类型/日期/金额）  │
│  ├─ Prompt 模板管理：问答/抽取各一套，版本化存放           │
│  └─ LLM 适配层：统一 OpenAI 兼容接口，供应商配置切换       │
│      （DeepSeek / 通义千问 / OpenAI，改环境变量即换）      │
├─ 数据模型层 ──────────────────────────────────────────┤
│  ├─ 开发期：SQLite（异步）；生产：PostgreSQL + pgvector   │
│  ├─ 向量存储：JSON 列 + numpy 内存检索（一期）            │
│  │   → 文档量上百份后切 pgvector + HNSW 索引（二期）      │
│  └─ 本地/对象存储：制度文档原件（Markdown/PDF）           │
└───────────────────────────────────────────────────────┘
```

**一次对话的流转**：前端请求 → 服务层鉴权与落库 → 编排层意图路由 →（问答）混合检索 + LLM 回答 /（报销）字段抽取 + 写入草稿表 → 消息回写、返回结果。

## 三、数据库表设计（6 张）

### 1. users — 用户
| 字段 | 类型 | 说明 |
|------|------|------|
| id | 整型主键 | 自增 |
| username | varchar(64) 唯一 | 工号/登录名 |
| password_hash | varchar(256) | PBKDF2 哈希 |
| role | varchar(16) | employee / admin |
| department | varchar(64) | 部门（抽取报销信息时直接引用） |
| is_active / created_at | | 状态与创建时间 |

### 2. chat_sessions — 会话
| 字段 | 说明 |
|------|------|
| id / user_id（外键） | 归属用户 |
| title | 会话标题（首条消息可自动摘要） |
| status | active / archived |
| created_at / updated_at | 时间戳 |

### 3. chat_messages — 消息
| 字段 | 说明 |
|------|------|
| id / session_id（外键） | 归属会话 |
| role | user / assistant / tool |
| content | 消息正文 |
| meta（JSON） | 意图分类结果、引用的制度条款、token 用量 |
| created_at | |

### 4. policy_documents — 报销制度文档
| 字段 | 说明 |
|------|------|
| id / title / doc_type | 类型：差旅标准 / 发票规则 / 审批流程 |
| file_path | 原件存储路径 |
| version | 同名文档重传则 +1，旧版归档 |
| status | processing / active / archived |
| uploaded_by（外键）/ created_at | 上传人与时间 |

### 5. policy_chunks — 文档切片（向量表）
| 字段 | 说明 |
|------|------|
| id / document_id（外键）/ chunk_index | 归属文档与序号 |
| content | 切片原文（如"第三条 北京住宿标准…"） |
| embedding（JSON） | 向量数组；二期切 pgvector 的 Vector 类型 + HNSW 索引 |
| token_count | 切片长度 |

### 6. expense_drafts — 报销单草稿
| 字段 | 说明 |
|------|------|
| id / user_id / session_id | session_id 记录来源对话，可回溯草稿怎么聊出来的 |
| status | draft / submitted（审批流二期） |
| expense_type / total_amount | 费用类型与总金额 |
| fields（JSON） | 抽取结果：日期、事由、明细行等 |
| missing_fields（JSON） | LLM 标记的缺失字段，驱动自动追问 |
| created_at / updated_at | |

## 四、第一周最小验证目标

**一句话验收**：员工登录后问"去北京出差住宿标准是多少"，系统能基于管理员上传的制度文档准确回答并标注出处；说"我要报销上周出差的打车费"，系统能通过追问补齐字段后生成一条草稿，管理员端能看到这条记录。

| 天 | 里程碑 |
|----|--------|
| 第 1–2 天 | FastAPI 骨架 + JWT 登录 + 两角色权限 + 建表 |
| 第 2–3 天 | 知识库链路：文档上传 → 解析 → 切片 → 向量化入库 |
| 第 3–4 天 | 对话链路：意图路由 + 混合检索 + LLM 回答，消息落库 |
| 第 5 天 | 报销链路：字段抽取 → 草稿落库 → 缺字段追问 + 列表接口 |
| 周末缓冲 | 管理端最小页面：文档上传 + 草稿/会话记录列表 |

**明确暂缓**（避免失焦）：OCR 发票识别、审批流引擎、财务系统对接、多级制度配置、SSE 流式输出。
