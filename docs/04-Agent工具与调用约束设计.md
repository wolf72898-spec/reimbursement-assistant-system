# 提示词 6 · Agent 工具（Function Calling）设计

> 目标：把报销助手从"固定流程问答"升级为"会自主决策的智能体"。
> 核心原则：**流程约束不能只靠提示词，必须在服务端代码里硬校验**——提示词负责引导模型走对路，服务端状态机负责兜底，模型"想跳步也跳不了"。

---

## 一、工具清单（7 个，按职能分三组）

### A 组 · 信息查询类（无副作用，可随时调用）

| # | 工具名 | 功能 | 关键参数 | 返回 |
|---|--------|------|----------|------|
| T1 | `search_policy` | RAG 检索报销制度条文（问答的唯一依据） | `question: str, top_k: int=3` | 条文片段 + 出处（文档名/条款号） |
| T2 | `get_expense_standard` | 查费用报销标准（住宿/交通/餐饮额度，按城市和职级） | `expense_type, city, level` | 标准额度 + 依据条款 |

### B 组 · 校验类（产生"凭证"，是建单的前置条件）

| # | 工具名 | 功能 | 关键参数 | 返回 |
|---|--------|------|----------|------|
| T3 | `validate_expense` | **核心校验器**：发票要素完整性、金额是否超标准、是否超 30 天时效、是否疑似重复/拆单报销 | `expense_type, amount, expense_date, invoice_info?, city?, level?` | `{status: passed/failed, violations: [...], ticket: {ticket_id, amount_digest, expires_at}}`（仅 passed 时发 ticket） |

### C 组 · 建单类（有副作用，受状态机强约束）

| # | 工具名 | 功能 | 关键参数 | 返回 |
|---|--------|------|----------|------|
| T4 | `create_draft` | 创建报销草稿（**必须携带 T3 签发的 ticket**） | `ticket_id, expense_type, amount, expense_date, details` | 草稿 id / 拒绝+中文原因 |
| T5 | `update_draft` | 补充/修改草稿字段（驱动"追问补齐"循环） | `draft_id, fields: dict` | 更新后草稿 / 拒绝+原因 |
| T6 | `get_my_drafts` | 查询当前用户草稿列表 | `status?` | 草稿数组 |
| T7 | `submit_draft` | 提交报销单进入审批（**要求 missing_fields 为空且状态=draft**） | `draft_id` | 提交结果 / 拒绝+原因 |

## 二、调用顺序约束（服务端状态机，代码级强制）

```
 ┌─────────┐   任意时刻     ┌────────────────┐  passed+ticket  ┌──────────────┐
 │ 空闲/问答 │ ───────────→ │ T3 validate     │ ──────────────→ │ T4 create    │
 │ T1/T2/T6 │              │ （有效期10分钟，  │                 │ （校验ticket， │
 └─────────┘               │  绑定金额摘要）    │                 │  金额不一致即拒）│
                           └────────────────┘                 └──────┬───────┘
                                    ↑ failed：返回违规原因，              │
                                    │        模型据此向用户解释或改方案     │ missing_fields
                                    └──────────────────────────────── │ 非空 → T5 update
                                                                      ↓ 补齐后
                                                              ┌──────────────┐
                                                              │ T7 submit    │
                                                              └──────────────┘
```

**五条硬约束（全部在服务端工具层校验，违反即返回错误事件）**：

1. **`create_draft` 必须携带有效 ticket**：T3 通过时签发 `ticket_id`（绑定用户 + 费用类型 + 金额摘要 SHA256 + 10 分钟过期）。T4 收到请求先验 ticket——不存在/过期/金额不一致 → 返回 `{"error": "VALIDATION_REQUIRED", "message": "金额或信息已变更，请先重新调用 validate_expense 校验"}`。
2. **金额变更即失效**：对话中金额被修改（如用户说"不对，是 88 元"）→ 旧 ticket 作废，必须重新 validate。防止"先校验 38 元、建单时写 380 元"的绕过。
3. **`update_draft` 不能绕过校验改金额**：修改 `amount` 字段时要求携带对应新金额的 ticket，否则仅允许改备注/明细描述类字段。
4. **`submit_draft` 双重门槛**：草稿状态必须为 `draft` 且 `missing_fields` 为空；提交时二次复核金额对应 ticket 未过期。
5. **违规即终止链路**：T3 返回 failed 时（超标准/超时效/疑似拆单），签发的是 `violation` 而非 ticket，T4/T5/T7 在该意图内全部拒绝——模型只能向用户解释原因，无法强行建单。

**为什么这样设计**：LLM 的指令遵循是概率性的，提示词只能"劝"，状态机才能"拦"。所有 C 组工具的拒绝响应都用中文错误码 + 修正指引写明"下一步该调什么工具"，模型收到后会自然回到正轨（自愈）。

## 三、系统提示词如何约束模型（三段式防线）

```
【第一段 · 流程规则（硬约束，编号列出）】
你必须严格遵守以下工具调用顺序，任何顺序错误都会被系统拒绝：
1. 涉及建单（create_draft）前，必须已通过 validate_expense 并获得 ticket；
2. 用户提供的金额、日期、费用类型与已校验内容不一致时，禁止使用旧 ticket，必须重新校验；
3. validate_expense 返回 failed 时，禁止调用 create_draft/update_draft/submit_draft，
   只能向用户说明违规原因和制度依据；
4. 信息不完整时先追问用户，禁止编造字段值（如日期、金额）填入草稿。

【第二段 · 行为准则】
- 制度问答只依据 search_policy 返回的条文，检索不到就明确说"制度中未找到"；
- 回答末尾附引用来源；
- 每次工具调用前，用一句话向用户说明你要做什么（如"我先核对一下差旅标准…"）。

【第三段 · 违规示例（few-shot 反例，让模型见过"错的样子"）】
错误示范：用户说"报销打车 38 元"→ 直接调用 create_draft ❌
正确示范：先 validate_expense(交通, 38, 日期) → 通过拿到 ticket → create_draft(..., ticket_id) ✅
```

**三段式防线的分工**：第一段让模型 95% 的情况下走对；第二段保证回答质量与可解释性；第三段把典型错误路径显式否定掉。剩下 5% 的漏网由服务端状态机兜底拦截——**提示词管引导，代码管生死**。

## 四、Agent 运行时架构（在现有系统上的改造点）

| 现状 | 升级后 |
|------|--------|
| `agent/router.py` 关键词二分（问答 vs 报销） | LLM 自主决策：把 7 个工具注册进 Function Calling，由模型决定调用序列 |
| `tools.py` 两个固定函数 | 工具注册表 `agent/registry.py`（OpenAI schema + 对应执行器 + 状态机守门） |
| 一次 LLM 调用出结果 | Agent 循环：`LLM → tool_call → 执行器（状态机校验）→ 结果回填 → LLM …` 最多 N 轮（防止死循环，默认 8 轮） |
| 提示词读 txt 文件 | 沿用提示词 5 的数据库模板机制，Agent 系统提示词也入库可配置 |

**每轮循环的事件流（复用提示词 4 的 SSE 通道）**：新增 `tool_call` 事件（前端显示"🔍 正在核对差旅标准…"之类的过程可见性）和 `ticket_state` 事件（前端显示校验状态徽章：待校验→已通过→已建单）。

## 五、分期落地建议

- **第一期（本次实现）**：7 个工具 + 服务端状态机 + Agent 循环 + SSE 过程事件 + 前端工具调用过程展示。validate_expense 用规则引擎（金额标准表 + 时效 + 关键词违规检测），不接发票 OCR。
- **第二期**：`validate_expense` 接入发票 OCR/验真 API；违规规则可配置化（管理员面板）。
- **第三期**：多轮跨会话记忆（用户常用出差地、职级自动带出）、并行工具调用。
